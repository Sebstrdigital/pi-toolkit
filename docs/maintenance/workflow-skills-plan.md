# Workflow and skills improvement plan

> **Proposal register only.** A listed improvement needs a later scoped decision
> before implementation. It neither changes instructions nor grants task,
> release, installation, or live-validation authority.

## Current direction to retain

- A clear, understood execution request carries ordinary reversible
  development authority; do not restore mandatory mode/Agreement ceremonies,
  forced three-agent slices, exhaustive manifests, repair quotas, or global
  serial-worker policy. Source: [lean workflows](../lean-workflows.md).
- Six-phase guidance is discoverable, optional, and uses the existing guarded
  execution boundary rather than a new runtime. Source:
  [Addy engineering](../addy-engineering.md).
- One-shot delivery remains a compatibility transport; progress is optional and
  is not a scheduler. Sources: [delivery workflow](../delivery-workflow.md),
  [progress](../progress.md).

## Superseded history and provenance

The old `tmux-runtime-correction` handoff is superseded as a next action by
accepted Phase C production integration; retain it as provenance. Delivery
implementation/activation folders similarly preserve snapshots and outcomes,
not current grants or defaults. The current source-facing guides above take
precedence for new work; explicit limits in an old active task remain binding.

## Non-goals

Do not turn proposals into compulsory documents, new agents, a scheduler,
settings changes, or worker/runtime changes. Diagrams are separately authorized
pending the user's style choice; they are not a workflow-plan implementation.
This plan preserves useful development and evidence over process production.
